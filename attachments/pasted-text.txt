Let’s separate the two:

1. Emulator “boot” vs real firmware boot
Right now your program probably:

Allocates memory

Loads a binary

Sets ProgramCounter

Flips some “initialized” flag

Starts a loop in Run()

From the emulator’s point of view:

“I’m up.”

From the firmware’s point of view:

“I haven’t even reached OEMInit, kernel init, or Mediaroom startup.”

A real boot means:

PC actually enters the CE kernel entry point from nk.bin

OEMInit runs

drivers probe hardware (your MMIO)

filesystem/registry mount

middleware EXEs start

UI loop or main service loop is reached

Until that happens, it’s not booted—it’s just a hypervisor with a loaded blob.

2. How to stop “fake boot” and force real boot
You need to tie “boot success” to firmware behavior, not emulator state.

Concrete checks:

PC range:  
Define: “CE kernel is running when ProgramCounter is between 0x8xxxxxxx and 0x8yyyyyyy (whatever nk.bin maps to).”

Instruction count:  
Don’t call it “booted” until at least N instructions have executed past kernel entry.

MMIO activity:  
Real boot will hit timers, IRQ controller, storage, network. If none of that happens, it’s not booting.

middleware signatures:  
Watch for known strings/functions in memory (e.g. Mediaroom EXE names, UI resources).

Your “hypervisor” should only say “initiated” when those conditions are met.
